# JobCompass 面试问答与学习入口

最后核对：2026-10-13。回答模板可按自己的理解修改；有功能变化时同步更新。下面只描述当前实现或明确注明的改进方向，不能直接把模板当成自己尚未掌握的经历。

## 一、项目与个人改造

### 1. 用一分钟介绍项目

我基于 Resume-Ai-Agent 二次开发了一个面向实习求职的岗位分析与准备规划系统。用户提供简历和最多三个目标岗位，系统提取要求、核对真实经历，用户复核后按每周时间预算形成准备计划，并跟踪任务与投递进度。

我重点实现了证据分析、多岗位预算安排以及计划确认和跟踪。后端使用 Java、Spring Boot、Spring AI，数据存 PostgreSQL；前端沿用 Next.js 并增加独立页面。AI 负责理解文本，引用校验、任务合并、预算与状态更新由 Java 和数据库处理。

学习入口：`README.md`、`docs/architecture.md`、`com.resumeai.compass`。

### 2. 上游已有功能与自己的改造分别是什么

上游提供简历上传、JD 管理、评分、知识库、改写与导出。我新增不可变简历版本和运行快照、受限读取工具、证据报告与人工复核、多岗位任务合并、预算草稿、幂等确认、任务和投递记录，并补充针对这些规则的测试与文档。

实际面试中应说明开源基线和自己的修改范围，并能展示源码、差异及验证依据。保留 MIT 归属，不把全部基础能力说成从零独立实现。

### 3. 为什么选择 Java 和 Spring AI

目标包含 Java 后端与 Agent 实习，Java 可以直接承载持久化、事务、版本控制和业务接口；Spring AI 提供模型调用、结构化输出及工具调用，与已有 Spring Boot 系统结合比较自然。它也便于我用熟悉的 Java 调试完整业务流程。

选型理由是当前学习目标和既有工程适配，不代表 Python 无法实现同样业务。

## 二、Agent 与证据分析

### 4. Agent 在这里具体做什么

新流程分为两阶段：先读取 JD 快照并提取要求，再读取指定简历版本逐条核对。模型通过 Spring AI 工具取得资料、生成结构化结果，Java 校验通过后保存报告。

计划排序、数据库写入和投递操作不交给模型决定。当前是有约束的分析流程，没有多 Agent 协作、自动抓取和自动投递。

源码：`SpringAiEvidenceModel.java`、`JobCompassReadTools.java`、`EvidenceValidator.java`。

### 5. Tool Calling 的过程与权限如何控制

模型选择工具及参数，Spring AI 在应用中执行对应 Java 方法，将返回内容用于后续回答。新流程有 `getResumeVersion`、`getJobSnapshot`、`listCandidateProjects`、`getApplicationHistory` 四个只读工具。

每次模型尝试创建独立工具对象，绑定本次运行、版本和岗位；工具参数必须匹配固定 ID，超过四次访问会拒绝。候选项目工具返回该版本原文段落，并未实现自动筛选真实项目的专门算法。

这个范围校验限制模型访问范围，不能代替未来多用户的身份鉴权和资料归属校验。

### 6. 为什么区分匹配、明确缺口和不确定

简历没写某项技能，无法证明用户不会。我把结果分为 `MATCH / GAP / UNCERTAIN`，匹配需要具体经历，明确缺口需要原文明确不满足条件，资料不足时保留不确定。

后端检查段落 ID、引文是否为对应原文的子串，以及每条要求是否恰好有一个判断。当前缺口校验采用保守的中文表述规则，适用范围有限；引用真实也不能保证模型理解一定正确，所以保留人工复核。

### 7. 如何处理幻觉和正文中的恶意指令

提示词规定外部正文只作数据，不执行其指令；工具限制读取范围；结构化输出经过字段、ID 和逐字引用校验。失败不会直接写成成功报告，用户复核单独保存。

评估样例包含 JD/简历指令诱导场景，但小样本通过不是安全保证。后续仍需扩充对抗样例、上下文边界和多用户权限测试。

### 8. 模型错误如何重试，是否存在死循环

要求提取与证据核对各最多两次尝试，可以带校验错误进行一次修正；模型调用设置 60 秒超时，传输重试为 0。两个阶段分别计尝试，不把 60 秒当成整个任务的总时限。

最终失败保留运行记录和错误码。用户手动重试会创建新运行，沿用旧版本和旧 JD 快照，不自动切换到最新资料。

### 9. RAG 用在哪里，是否用于判断用户能力

上游知识库将规则文档分块、向量化并存入 pgvector，检索后用于旧分析/改写。新证据流程目前直接读取简历和 JD 快照，没有接入知识库召回。

知识库可以帮助提出建议，但不能用一篇 Redis 教程证明用户做过 Redis 项目。后续接入时需要保留这个边界。

源码：原 `RagKnowledgeService.java`；新 `SpringAiEvidenceModel.java`。

## 三、Java 后端与业务规则

### 10. AI 很慢，如何避免请求一直等待

提交后创建运行记录，将模型分析放入本机有界线程池：2 个工作线程，等待队列容量 8。接口返回运行 ID，报告页每两秒查询状态，成功或失败后停止轮询。

队列满时返回 429 并保留失败记录。当前不是 Redis 队列或消息队列；重启会把遗留任务标记为中断，需要用户手动重试。也没有跨实例领取和恢复能力。

源码：`EvidenceService.java`、`frontend/src/app/evidence-analyses/[id]/page.tsx`。

### 11. 多个岗位的任务怎么合并

先用明确的技能别名映射归一化，再按“技能键 + 行动类型”分组。同组保留全部岗位和要求来源，建议耗时取较大值，避免简单相加重复学习时间。未知技能按要求 ID 独立处理，不靠模糊相似度盲目合并。

人工复核可以纠正支持的技能键。Redis 基础与一致性设计、Java 与 JavaScript 不应该因为名称相近就合并。

源码：`BudgetPlanner.java`；测试：`BudgetPlannerTests.java`。

### 12. 如何决定准备顺序

每个岗位的必备要求权重为 3、加分要求为 1，再乘用户设置的岗位重要程度 1–3；同岗位对一组任务只取最高权重，跨岗位求和形成收益。收益除以预计小时数得到优先值。

按优先值、截止日期和稳定键排序，依次选择预算能容纳的任务。高优先任务太贵时继续看后面的便宜任务，不立即停止。它是可解释的贪心规则，不保证全局最优；截止日期用于同优先值排序和提醒，不是硬性可投递保证。

### 13. 计划确认为什么需要事务和幂等

确认会修改计划状态、为来源岗位创建或复用申请并记录事件，这些写入需要一起成功或回滚。使用短事务锁住计划，结合确认键、内容哈希及唯一约束处理重复和并发请求。

相同计划/相同键重复确认复用结果；不同内容或计划占用同一键会冲突。已有投递记录保留原状态，数据库唯一岗位约束避免重复创建。模型网络调用在这些事务之外执行。

源码：`PlanningService.confirm`；测试：`CompassPostgresIT.java`。

### 14. 乐观锁在哪里，为什么又用行锁

这里没有在新模块上使用 JPA `@Version`。新复核、草稿、任务与申请更新携带期望版本，SQL 条件包含 `WHERE version = ?`，成功后递增版本；旧版本提交返回冲突。

计划草稿/确认/任务更新还会对计划做短行锁，以串行化该计划内的相关操作。行锁处理聚合内竞态，版本检查处理用户拿着旧页面覆盖新内容，两者解决的问题不同。

### 15. 为什么保存简历版本和 JD 快照

简历之后会修改，岗位要求也可能改变。报告必须能够追溯当时的资料，所以分析绑定固定简历版本，并保存运行所用 JD 快照；复核和计划也保留其来源。

SHA-256 用于内容标识与查重，不等于数据库唯一约束或防伪签名。旧报告不会因新版上传或任务完成而自动改写。

### 16. 为什么用 PostgreSQL，Redis 做了什么

原项目将关系数据与 pgvector 放在同一 PostgreSQL 中，我沿用后减少迁移范围。新模块使用 JDBC 保存业务和实现事务，上游实体继续使用 JPA；Flyway 管理迁移。

Redis 当前用于保留的基础检查等能力，新分析进度存数据库，本机线程池不由 Redis 承载。项目没有已经实现的 Redis 分布式队列、Redisson 锁或缓存击穿方案。

### 17. Docker 与 IDEA 是什么关系

Docker Compose 启动数据库、Redis 和兼容 MinIO API 的 Silo。Java 后端在 IDEA/命令行运行，前端通过 Node 运行；本机应用用 `localhost` 连接映射端口。

目前没有完整前后端 Dockerfile 或云平台自动部署。使用容器数据库不要求在 Windows 再安装 PostgreSQL，也不意味着数据存在云端。

## 四、验收、局限与演示

### 18. 怎么证明功能可行，测试数字如何表述

常规测试验证引用、快照、预算和文件边界；真实 PostgreSQL 测试验证并发、事务回滚和版本冲突；真实模型测试用人工标注的虚构案例检查输出与引用。另用浏览器走通三岗位到计划确认及投递更新。

历史结果为常规 13 项、数据库 9 项通过，15 个模型样例标签一致、负例误判 MATCH 为 0。只能称为这些样例的结果，不能写“准确率 100%”“高并发性能领先”等没有依据的指标。

依据：`docs/验收记录.md`、评估 JSON、相关测试类。

### 19. 项目最大的限制，下一步会改什么

当前是单用户、本机队列；没有自动抓取、投递、身份鉴权和多实例调度。证据规则保守，模型理解仍可能出错；耗时需要用户确认，贪心安排不保证最优。

可以先增加稳定演示输入和 CSV 导入，再按实际需要完善持久化队列、权限隔离或检索建议。按实施计划选一项做完并验证，不用同时堆框架。

### 20. 面试现场怎么展示

先启动基础服务、后端与前端，使用虚构资料演示：固定简历版本 → 两三个岗位分析 → 点开引用 → 人工复核一项 → 设置预算 → 看合并任务来源 → 保存确认 → 更新任务和投递 → 查看事件。

如果模型或网络不可用，使用已有成功报告说明其历史生成时间，不把历史结果冒充现场新生成结果。准备好 `BudgetPlanner`、证据校验与确认事务的源码，能够解释每个选择的理由。

### 21. 如何证明 Agent 优化有效

为证据分析增加每任务/每阶段统计，包含校验失败重试和用量缺失状态。将 40 个虚构单要求样例分成 25 个开发、15 个独立验收，对 FULL/COMPACT 工具快照交替配对比较，保持全部原文分段、提示词和校验不变。

本轮各模式完成 40 / 40，标签一致 40 / 40；累计输入 Token 从 136,738 降至 127,864，减少 6.49%，输入+输出合计减少 5.03%。平均耗时从 6.14 秒变为 6.32 秒，不能写提速或费用下降。只可表述“在这 40 组单轮虚构样例上”，后续复杂多要求、长文本、不同模型和并发仍需验证。新分析读取固定快照，本次没有测知识库召回命中率。

源码入口：`AnalysisMetrics`、`SpringAiEvidenceModel`、`JobCompassReadTools`、`CompassLiveModelIT`；原始数据及局限见 [验收记录](验收记录.md) 与 [对照结果](jobcompass-evaluation-comparison.json)。
