## 一、Spring AI 相关概念与 Agent 工程

### 01 Java AI 框架如何选型

<a id="bg01"></a>

> 我会先看现有后端和业务需要，再比较模型、工具、检索、输出转换等能力能否接入。还要看配置、持久化和测试是否容易复用，而不是只比较 API 是否简短。本项目已有 Spring Boot，所以选择 Spring AI，把模型调用接到现有业务中；事务、恢复和最终写入仍由后端负责。

**追问：有了统一接口，更换供应商是不是只改配置？**

> 不一定。统一接口能减少改动，但不同供应商对工具调用、结构化输出和参数的支持仍有差异。项目还使用 OpenAiChatOptions，更换后要重新验证判断、引用、错误处理和用量，不能只确认接口连通。

**项目对照：** [依赖声明](../backend/pom.xml)使用 Spring AI 2.0.0 与 Spring Boot 4.1.0；[SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)使用 `ChatClient`。项目没有接入 LangChain4j、LangGraph 或 Spring AI Alibaba，不能把文章里的接口名当成本项目实现。

### 02 Workflow、Agent、Tools 的区别

<a id="bg02"></a>

> 可以从控制流程的角度区分。Tools 提供具体能力，比如读简历；Workflow 由程序安排主要步骤和分支；Agent 则让模型根据上下文选择下一步行动。它们可以组合使用。这个项目由 Java 安排提取和核对，模型在阶段内请求受限工具，预算计算也交给 Java。

**追问：两次模型调用，能不能说成两个 Agent？**

> 不能只按调用次数算。两个阶段即使提示词不同，也可能只是同一条程序流程。当前没有多个独立角色之间的协商和动态分工，所以我会按实际实现介绍为两阶段工具工作流。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)由 Java 安排“提取要求→核对经历”，每阶段注册只读工具；[BudgetPlanner](../backend/src/main/java/com/resumeai/compass/BudgetPlanner.java)由 Java 规则合并和安排任务。当前不是多 Agent 自主协作系统。

</details>

### 03 上下文工程与 Prompt、Memory 的区别

<a id="bg03"></a>

> 上下文工程主要解决“这一轮让模型看到哪些信息”。Prompt 说明任务和规则，Memory 管理历史，而上下文工程还要决定带入哪些资料、状态、工具定义和结果，并控制体积。项目的 COMPACT 就是在保留 ID 和全部原文分段的前提下，移除重复正文和部分元数据。

**追问：Token 少了，就能证明上下文优化成功吗？**

> 还不能。要看关键事实是否丢失，尤其是否认和限制条件，以及判断质量、失败和耗时有没有变化。项目有这批 FULL/COMPACT 对照，但不能据此保证所有长文本都会得到同样收益。

**项目对照：** [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)的 FULL/COMPACT 返回不同快照结构；COMPACT 移除重复元数据，保留 ID 和全部原文分段，没有实现摘要式长期记忆。历史对照见[评估结果](jobcompass-evaluation-comparison.json)，小样本不代表普遍收益。

> 原文短摘录：这一轮让模型看到什么

</details>

### 04 Agent 效果如何评估

<a id="bg04"></a>

> 我会同时看结果、过程和资源。结果看任务是否完成、判断与引用是否符合预期；过程看工具、参数和步骤有没有出错或越界；资源看耗时、Token、失败及重复运行表现。先给样例定义成功条件，能用规则检查的先自动检查，开放质量再结合人工评价。

**追问：接口返回成功，为什么还要做质量评估？**

> 接口成功只说明请求完成，不说明结论有依据。比如返回了完整 JSON，里面的引用仍可能是假的。项目会再查 ID、原文和标签，历史 40 组结果也只说明那批样例，不能直接说成通用准确率。

**项目对照：** [AnalysisMetrics](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)记录阶段尝试、耗时、工具次数、失败码及返回用量；[既有评估文件](jobcompass-evaluation-comparison.json)保留 40 组 FULL/COMPACT 对照。现有记录不等于完整 Trace 平台或线上 A/B 系统，标签一致率也不是通用准确率。

> 原文短摘录：Agent 评测不能只看最终答案

</details>

### 05 Function Calling 与 MCP 的区别

<a id="bg05"></a>

> Function Calling 让模型表达“要调用哪个工具、传什么参数”，实际执行由应用完成。MCP 则规范工具等能力怎样接入、发现和复用，两者可以配合。项目通过 @Tool 定义 Java 方法，再注册给 ChatClient，目前没有实现 MCP Client 或 Server。

**追问：一个 Java 方法加了 @Tool，就成为 MCP 服务了吗？**

> 没有。@Tool 是应用内方法的描述和调用机制，MCP 还需要协议层接入。模型能调用一个方法，并不代表这个方法已经作为 MCP 服务对外提供。

**项目对照：** [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)使用 `@Tool`，由 `.tools(tools)` 注册到 ChatClient；当前是应用内工具，没有实现 MCP Server/Client。

<summary>题源、原文摘录与补充要点</summary>

原文：[MCP 和 Function Calling 有什么区别？](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html)，重点读两者分层和选型。

> 原文短摘录：两者是不同抽象层次的东西

**来源要点（转述）：** Function Calling 涉及模型表达调用意图及参数，宿主程序执行工具并回传结果；MCP 侧重工具接入、发现与复用的协议。两者可以配合，不能仅因为函数能被模型调用，就称其为 MCP 服务。

</details>

### 06 工具格式错误、超时与失败如何处理

<a id="bg06"></a>

> 先看错误发生在哪一层。格式或参数错误可以给出明确反馈，允许有限纠正；权限或业务规则不允许的调用应直接拒绝；瞬时网络故障才考虑有限重试。如果调用可能写数据，还要先判断上次是否已经执行。项目工具只读，阶段最多尝试两次，计划写入的幂等由业务服务另外处理。

**追问：工具超时，直接重试为什么可能出错？**

> 因为超时不代表远端没执行。比如写入已经成功，只是响应丢了，原样重试可能再写一次。需要稳定幂等标识和结果查询，不能单凭本地超时决定重做；项目目前没有完整的外部副作用恢复机制。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)每阶段最多两次尝试，附带纠错信息；工具每次尝试重新创建且最多四次访问。这是模型阶段重试，不等于每个 HTTP 请求最多两次。写入幂等由 [PlanningService.confirm](../backend/src/main/java/com/resumeai/compass/PlanningService.java)负责，当前没有实现文章中的完整熔断、Checkpoint 调度和外部副作用恢复。

> 原文短摘录：先分类，再处理

**来源要点（转述）：** 格式不合法、业务参数错误、无权限、瞬时故障及执行结果未知，处理方式不同。有副作用的调用需稳定幂等标识；超时后不能直接认定没执行，必要时先查询结果。重试应限制次数与时间。

</details>

### 07 模型查数据库时如何限制权限与泄漏

<a id="bg07"></a>

> 权限应由后端决定。多人场景先从登录态确定用户，再检查资料归属，通过查询和工具限制对象、字段与次数，只返回需要的内容。工具结果仍是不可信外部数据。项目目前只做了绑定快照的只读工具和 ID 范围检查，还没有多用户认证与租户隔离。

**追问：把用户 ID 写进提示词，能不能防止越权？**

> 不能。提示词中的 userId 和模型生成参数都不是可信身份。后端必须根据登录态强制检查资料归属，不能让模型决定自己有权读谁的数据。

**项目对照：** [JobCompassReadTools.check](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)校验当前运行绑定的 ID，只暴露固定快照，没有任意 SQL 和写工具。当前仍是单用户范围，ID 范围检查不代表已经实现多用户认证、租户隔离或完整安全体系。

### 08 人工确认如何落实到程序

<a id="bg08"></a>

> 人工确认需要成为明确的业务操作。用户先看到待确认内容，后端再检查内容、版本和状态，通过幂等与事务保存结果。项目里模型判断和人工复核分别保存，预算先形成草稿，确认后才进入后续跟踪。模型在回复里说“已确认”，不算真的完成确认。

**追问：用户确认以后，是否就等于执行成功？**

> 不一定。用户点击只表达了操作意图，请求还可能因为版本冲突或数据库错误失败。页面要以服务端保存的状态为准，并让重复请求能够查询或复用结果。

**项目对照：** [PlanningService.confirm](../backend/src/main/java/com/resumeai/compass/PlanningService.java)结合行锁、确认键和内容哈希；[ExperienceService.confirm](../backend/src/main/java/com/resumeai/compass/experience/ExperienceService.java)保存用户确认的证据卡快照。二者是业务确认流程，不是跨系统通用审批引擎，也不会自动向外投递简历。

## 二、RAG 与知识库

### 09 RAG 的完整流程

<a id="bg09"></a>

> RAG 通常有离线和在线两部分。离线先解析文档、分块、生成向量并建索引；在线根据问题检索相关片段，把片段和问题一起交给模型回答。查询改写、重排是按需增加的环节。项目上游知识库有建索引、搜索和删除功能，新证据分析则直接读固定简历与岗位，不经过向量召回。
>
> 对应原实现，KnowledgeDocumentApplicationService.create 只存正文，index 才删除旧索引、分块并调用 VectorStore。AnalysisApplicationService 根据 useRag 查询四条建议，改写则通过 retrieveGuidance 工具检索。种子知识启动时只保存文档，不会自动向量化。

**追问：用了 RAG，为什么还可能出现错误答案？**

> 因为检索可能漏掉关键资料，模型也可能误解检索内容或额外推断。所以还要核对来源与结论，证据不足时保留不确定，也不能拿教程证明用户做过相关实践。

**原项目继续学习：** [Q129](面试问答.md#q129)、[Q131](面试问答.md#q131)、[Q157](面试问答.md#q157)。

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)有 `index/search/deleteIndex`；原工具 [ResumeOptimizationTools](../backend/src/main/java/com/resumeai/agent/ResumeOptimizationTools.java)可使用知识检索。新证据链读取固定简历/JD 快照，不能把该链称作向量召回分析。

### 10 文档分块与粒度如何选择

<a id="bg10"></a>

> 块太大会混入无关内容、增加输入，太小又可能切断上下文，所以要按实际查询评估。重叠能缓解边界损失，但会增加重复。项目按段落组块，最大长度为 1800 个 Java 字符，只有超长段落切分时重叠 180 个字符，普通段落块没有统一重叠。结构分块或父子块是其他方案，不是当前实现。

**追问：为什么不能把1800字符说成1800 Token？**

> 因为字符长度和模型分词是不同单位。当前按 Java 字符长度切分，没有使用 TokenTextSplitter。实际 Token 数还受语言、符号和模型分词影响，调参要同时看检索效果与真实用量。

**项目对照：** [RagKnowledgeService.splitIntoChunks](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)先聚合段落，长段落按最多 1800 个 Java 字符单位拆分并重叠 180；普通段落块没有统一加重叠。这不是 1800 token，也没有实现语义切分、父子检索或 Late Chunking。

<details>
<summary>题源、原文摘录与补充要点</summary>

原文：[文档存储与 Chunking 策略](https://xiaolinnote.com/ai/rag/4_chunking.html)，重点读固定窗口、语义边界、父子块的取舍。

> 原文短摘录：粒度选择没有银弹

**来源要点（转述）：** 块太大影响局部匹配和输入预算，块太小容易失去上下文；重叠、结构边界和父子块分别解决不同问题。文档类型与实际召回评估决定取舍，文章中的 token 范围是示例起点。

</details>

### 11 Embedding 是什么，怎样选模型

<a id="bg11"></a>

> Embedding 把文本转换成数值向量，用于比较相关程度。选模型时，我会拿业务里的语言、领域和查询做测试，比较能否找回正确片段，再看部署、成本和现有索引约束。项目分别配置聊天与向量模型，不能因为聊天接口可用，就认为 Embedding 也已接通。

**追问：换成同维度的模型，可以保留旧向量吗？**

> 通常不能直接保留。维度相同不代表向量空间兼容，一般要用新模型重建历史向量并验证检索；维度改变时，还要迁移列和索引。

**项目对照：** 本项目聊天与向量化可分别配置，向量索引依赖向量模型；[依赖](../backend/pom.xml)包含 pgvector 集成。改模型时还要检查维度和已有索引，不能只改模型名称。文章中的 Hit@K 示例不代表本项目实测结果。

<details>
<summary>题源、原文摘录与补充要点</summary>

原文：[Embedding 的含义、选择与评估](https://xiaolinnote.com/ai/rag/6_embedding.html)，重点读业务数据评测。

> 原文短摘录：语义相近的文本向量距离近

**来源要点（转述）：** Embedding 把文本映射到可比较的数值空间。候选模型要结合语言、领域、部署约束和成本，用业务问题与正确片段评估 Hit@K；排行榜和别人项目里的示例数字不能替代自己的测试。

</details>

### 12 向量检索与关键词检索如何互补

<a id="bg12"></a>

> 关键词检索适合名称、编号等精确匹配，向量检索适合表达不同但语义相近的内容。混合方案可以分别召回，再去重和融合，但要验证收益。项目当前先查向量，异常或没有结果才回退到文本 contains 查询，TopK 限制在 1 到 10。

**追问：失败后走文本检索，算不算混合召回？**

> 这里更准确地说是回退查询。两路没有同时召回和融合，也没有 BM25、RRF 或 rerank。如果增加这些环节，还要处理重复候选和不同分数，并比较质量、延迟与成本。

**项目对照：** [RagKnowledgeService.search](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)先调用向量检索，异常或无结果才走文本查询，TopK 被限制在 1–10。这里的回退查询不是 BM25 检索、双路并行召回、RRF 融合或 Rerank；这些功能目前都没有接入。

<details>
<summary>题源、原文摘录与补充要点</summary>

原文：[向量检索和关键词检索的区别](https://xiaolinnote.com/ai/rag/11_retrieval_types.html)，重点读精确词、语义与混合检索。

> 原文短摘录：两者是互补关系

**来源要点（转述）：** 词项检索擅长处理明确名称与术语，向量检索适合语义近似表达；混合方案可多路召回后融合排名。应区分多路融合与失败后备用查询，两者的执行方式和效果不同。

### 13 怎样降低幻觉并核对引用

<a id="bg13"></a>

> 我会要求模型基于资料回答，没有证据就保留不确定；返回后核对来源 ID 和逐字引用，再检查引用能否支持结论。项目 EvidenceValidator 检查要求、段落、引文和字段规则，语义疑点仍交给用户复核。新流程虽然不走 RAG，也同样采用这种证据约束。

**追问：原文引用完全正确，为什么还不能证明判断正确？**

> 因为真实句子也可能被断章取义。比如简历只写了 Redis 缓存，引用完全正确，也不能因此认定做过分布式锁。逐字校验能发现伪造引文，但不能保证语义推断正确。

**项目对照：** [EvidenceValidator](../backend/src/main/java/com/resumeai/compass/EvidenceValidator.java)检查要求 ID、段落 ID、逐字引用和判断字段；新流程虽不是 RAG，也采用可追溯证据约束。`entity(...)` 成功不代表事实正确，逐字引用正确也不保证语义判断正确，仍保留人工复核。

### 14 何时用 RAG，何时直接读取资料

<a id="bg14"></a>

> 资料量大、需要反复查局部内容时，我会考虑 RAG；资料少、要求整体核对时，可以直接读取全文；需要沿线索继续查找时，再评估受控的自主检索。项目知识库用索引提供建议，新分析则通过工具读取固定版本原文，没有让模型自由搜索本机文件。
>
> 原知识建议有两条调用路径：旧分析直接拿 JD 查知识库，改写模型按需要请求检索工具。查询异常或空结果才查标题、正文包含整个 query 的记录；这与新流程固定读取个人经历的证据用途不同。

**追问：检索到了几个相关片段，是否代表已经覆盖全部证据？**

> 不能。返回几个相关片段，只说明找到了这些内容，不能证明其他位置没有限制或相反信息。要明确检索覆盖范围和资料版本，未覆盖时保留不确定，而不是把局部命中当成完整证据。

**项目对照：** 原知识库用向量索引提供写作知识；新分析通过 [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)读取固定版本原文。它是受限快照读取，不是模型自由搜索本机文件；引用范围与资料版本有明确边界。

### 15 IoC、依赖注入与 Spring Boot 装配

<a id="bg15"></a>

> IoC 把对象创建和组装交给容器，依赖注入是容器提供依赖的方式。Spring Boot 再根据类路径、属性和条件自动装配组件。项目服务用构造器声明依赖，但每次阶段尝试的工具对象由业务代码自行创建，不能把所有 new 出来的对象都当成容器 Bean。

**追问：把依赖声明成 final，服务就线程安全了吗？**

> 不是。final 固定引用，不能保证对象内部不变化。单例服务仍要避免共享请求数据，项目为每次运行和阶段尝试创建独立统计及工具上下文，就是为了减少不同任务数据混用的风险。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)通过构造器注入 Builder、校验器等；每次尝试的工具由代码 `new` 出来。Boot 自动配置的具体加载机制需按当前版本核对，不能直接套用旧版 `spring.factories` 教程。

### 16 Spring 事务与代理边界

<a id="bg16"></a>

> 声明式事务通常依赖代理，同类内部直接调用可能绕过增强；方法条件、异常和回滚规则也会影响结果。项目新模块用 TransactionTemplate 明确短数据库事务，把慢模型调用放在外面。旧改写流程仍有原来的事务范围，不能说全项目都已经统一调整。
>
> 原 ResumeRewriteService.create、regenerate 在注解事务方法中调用模型；exportMarkdown、exportPdf 虽标 readOnly，仍会上传对象。readOnly 不是外部操作禁写开关。原上传又没有新增 PDF 入口的失败删除补偿，所以不能把新流程的事务与补偿结论套给所有旧方法。

**追问：用了数据库事务，为什么还需要文件删除补偿？**

> 因为数据库本地事务不会自动撤销对象存储请求。新增 PDF 上传在业务保存失败时会尝试删文件，但补偿本身也可能失败，所以后续仍需要可靠记录和对账。

**原项目继续学习：** [Q145](面试问答.md#q145)、[Q151](面试问答.md#q151)。

**项目对照：** 新业务 [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)、[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)使用 `TransactionTemplate` 控制短事务，模型调用在其外部。原 [ResumeRewriteService](../backend/src/main/java/com/resumeai/application/rewrite/ResumeRewriteService.java)仍有既有事务结构，不能把新模块的取舍描述成全项目都已完成的改造。

### 17 线程池参数、任务队列与执行顺序

<a id="bg17"></a>

> 七个参数是核心线程数、最大线程数、空闲时间及单位、工作队列、线程工厂和拒绝策略。提交时先考虑核心线程，再入队，队列满后才尝试扩到最大数，仍无法接收就拒绝。项目证据分析池是两个工作线程、八个等待位置；经历补充另有一个线程、四个等待位置的独立池。

**追问：增加队列容量，能解决长期排队吗？**

> 如果任务长期进入得比处理得快，扩大队列只会增加等待和内存占用。我会先看执行与排队耗时、下游配额及资源，再调整任务受理上限和执行并发。这些只是当前配置，还没有通过压测确定系统的处理能力。

**项目对照：** [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)采用 2 个工作线程、8 个等待名额、`AbortPolicy`；[ExperienceService](../backend/src/main/java/com/resumeai/compass/experience/ExperienceService.java)采用独立 1 线程和 4 个等待名额。配置是资源边界，不是经过压测的吞吐承诺。

原文：[Java 并发编程面试题](https://xiaolincoding.com/interview/juc.html)，站内查找 `线程池的参数有哪些`、`工作原理`。

> 原文短摘录：复用线程、控制并发数量

**来源要点（转述）：** 结合核心/最大线程、存活时间、队列、工厂及拒绝处理理解任务接纳过程；队列有无上限会影响扩容与积压。

</details>

### 18 拒绝策略与原子计数

<a id="bg18"></a>

> 项目用 AbortPolicy 明确报告任务受理失败，业务捕获后保存失败状态并返回 429。如果改成 CallerRunsPolicy，HTTP 提交线程可能去执行慢模型；静默丢弃又可能留下未结束状态。工具次数另外使用 AtomicInteger 原子递增，它只保护计数，不负责整个工具执行或数据库事务。

**追问：有了原子计数和任务状态，重启后能自动继续吗？**

> 不能。原子计数在进程内生效，数据库状态也不会保存线程执行位置。当前重启会把遗留任务标为中断失败，自动领取和接管还没有实现。

**项目对照：** 队列拒绝后 [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)保存失败状态并返回 429；工具用 `AtomicInteger.incrementAndGet()`计数并限制访问。进程重启将遗留任务标为 `INTERRUPTED`，没有持久队列自动接管。

<summary>题源、原文摘录与补充要点</summary>

**来源要点（转述）：** CallerRunsPolicy 占用提交方；AbortPolicy 使接纳失败可见。原子类保护单次更新，不会自动提供整个业务事务。

### 19 HashMap、HashSet 与业务去重

<a id="bg19"></a>

> Map 用来查找和分组，Set 用来去重，项目用它们合并准备任务并检查重复报告、岗位。相等对象需要相同 hashCode，但哈希相同可能只是冲突，键还要保持稳定。内存集合的去重只覆盖当前数据，普通集合也不会因为放在 Spring 服务里就自动线程安全，数据库写入仍要约束和事务。

**追问：先用 Set 去重，再入库，为什么还可能重复？**

> 因为并发请求可能各自用一个 Set，都认为记录不存在，然后同时插入。跨请求、跨实例的唯一性要由数据库业务唯一约束保护，应用再处理冲突或复用结果。

**项目对照：** [BudgetPlanner](../backend/src/main/java/com/resumeai/compass/BudgetPlanner.java)使用集合组织技能与任务合并；[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)用 Set 检查重复报告/岗位。进程内去重不代替数据库唯一约束，预算排序也不是全局最优求解。

### 20 ACID、锁、版本与幂等

<a id="bg20"></a>

> ACID 分别是原子性、一致性、隔离性和持久性。在计划确认中，事务让相关数据库操作一起提交或回滚，行锁协调同一计划的竞争，版本检查拒绝旧页面更新，幂等键和唯一约束处理重复与冲突。项目使用 PostgreSQL 17，隔离和锁的行为要按 PostgreSQL 解释。

**追问：已经加行锁，为什么还要 expectedVersion？**

> 因为拿到锁只能说明当前可以执行，不说明用户页面里的数据是最新的。expectedVersion 告诉后端这次修改基于哪个版本，可以拒绝旧内容覆盖；两者解决的时点不同。

**项目对照：** [SnapshotService](../backend/src/main/java/com/resumeai/compass/SnapshotService.java)锁父记录分配版本号；[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)组合 `FOR UPDATE`、版本条件、确认键、内容哈希及唯一约束。当前使用 PostgreSQL 17，不可套用 InnoDB 的聚簇索引、间隙锁或默认隔离级别；隔离细节见 [PostgreSQL 17 官方文档](https://www.postgresql.org/docs/17/transaction-iso.html)。

**来源要点（转述）：** 事务保证一组相关变更的提交边界；并发更新还需理解隔离、锁与约束。数据库的具体行为依赖实现与配置。

</details>

### 21 Redis 缓存雪崩、击穿与穿透

<a id="bg21"></a>

> 雪崩是大量缓存同时失效或服务故障，击穿是热点失效后大量请求一起回源，穿透是反复查本来不存在的数据。可以分别考虑过期时间打散与降级、受控重建和短期空值。缓存更新还要处理并发和失败窗口，不能只配置过期时间。项目新分析目前没有落地这些缓存治理。

**追问：写库后删除缓存，就能保证强一致吗？**

> 不能直接保证。并发回填或删除失败仍可能留下旧值，需要根据允许的不一致时间设计重试、版本和其他措施。项目当前只保留 Redis 基础服务与健康检查，这里是原理和候选方案。

**项目对照：** Redis 是上游保留基础服务；[RedisHealthService](../backend/src/main/java/com/resumeai/infrastructure/redis/RedisHealthService.java)提供健康检查。新分析状态存在 PostgreSQL，队列在 JVM 内存中，没有把上述缓存治理、Redis 队列、分布式锁或 Bloom Filter 做成当前成果。本条按基础扩展复习。

原文：[Redis 面试题](https://xiaolincoding.com/interview/redis.html)，站内查找 `缓存雪崩、击穿、穿透` 与 `数据缓存一致性`。

> 原文短摘录：事务提交成功后，再删除缓存

**来源要点（转述）：** 区分大量缓存同时失效、热点单键失效与查询不存在数据；缓存与数据库之间存在失败窗口，需要根据可接受的旧数据时间选择失效、重试等措施，不能天然承诺强一致。

</details>

### S01 Spring AI 解决什么问题，为什么不直接调厂商 API？

> 直接调厂商 API 也能完成模型调用，Spring AI 的价值主要是减少接入时的重复工作。它把模型、向量存储和工具组织成应用接口，并能结合 Spring 配置、注入与观测。项目使用 ChatClient 组织请求，同时保留 OpenAiChatOptions，所以供应商差异并没有完全消失，具体能力仍要验证。

**追问：什么情况下仍要关注厂商原生 API？**

> 如果需要统一接口之外的参数或模型特性，就要查看厂商 API 和框架适配情况。即使接口名称统一，工具、输出约束和用量返回也可能不同，我会按项目锁定版本做实际回归。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)统一使用 ChatClient，但仍构造 `OpenAiChatOptions`；接入兼容接口不能据此认定所有供应商行为相同。

<a id="sa02"></a>
### S02 ChatClient 与 ChatModel 如何分工？

> ChatModel 负责抽象底层模型交互，ChatClient 在上面提供更方便的请求组织方式，例如消息、选项、工具、Advisor 和结果转换。项目注入 ChatClient.Builder，再用 prompt、system、user 构造调用。链式写法不代表流式，是否流式要看选择的调用方式。

**追问：调用 call()，是不是立即发出了模型请求？**

> call() 先选择同步调用方式，实际获取 content、chatResponse 或 entity 等结果时才触发调用。所以定位异常和计时，要看真正获取结果的位置，不能只看到 call 这个名字就认定请求已经发出。

**项目对照：** [模型构造器](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)注入 `ChatClient.Builder` 后构建客户端；业务通过 `.prompt().system(...).user(...).call().entity(...)`取得结果。

<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q2](#spring-g1)；另见 [G2 Q3](#spring-g2)。

**要点：** ChatModel 是模型调用抽象；ChatClient 在其上提供链式消息构建、默认值、Advisor、工具及类型化结果等便利能力。ChatClient 同时支持同步与流式，“fluent API”不意味着每次调用都是流式。[官方 Chat Client API](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

### S03 Starter、自动配置和 BOM 分别做什么？

> Starter 主要引入一类集成需要的依赖，自动配置根据类路径、属性和条件创建 Bean，BOM 则统一一组依赖版本。它们是配合关系，BOM 本身不会把所有能力都启用。项目导入 Spring AI BOM，并使用模型和 pgvector Starter，升级时还要核对与 Spring Boot 的兼容范围。
>
> 原结构化还有一个装配例子：模型网关依赖 ChatClient.Builder 并标 Primary，同时保留规则网关。Primary 决定注入优先，模型异常后的回退则来自方法中的 try/catch，二者不是同一个机制，其他服务也仍可能直接依赖 ChatClient.Builder。

**追问：pom里有某个Starter，就说明对应能力已启用了吗？**

> 不说明已经启用。还要看装配条件是否满足、Bean 有没有创建，以及业务是否真的调用它。依赖存在、服务启动和功能质量通过，是不同层面的证据。

**原项目继续学习：** [Q126](面试问答.md#q126)。

**项目对照：** [pom.xml](../backend/pom.xml)导入 `spring-ai-bom`，引入 OpenAI、Ollama 和 pgvector Starter。依赖存在不等于这些模型当前都已启用或验证，不读取私有配置猜测运行状态。

**要点：** Starter 引入集成依赖，自动配置按条件创建相关 Bean；BOM 管理一组兼容依赖版本，本身不代表已经启用全部能力。官方列出 Spring AI 2.0.x 对应 Boot 4.0.x/4.1.x，升级应先核对兼容范围。[官方 Getting Started](https://docs.spring.io/spring-ai/reference/getting-started.html)

### S04 PromptTemplate 与 system/user 消息有什么用？

> Prompt 用来组织消息和选项，PromptTemplate 通过变量替换复用提示结构，system 和 user 则区分消息角色。项目当前用 Java 文本块构造提示，再把运行 ID 和资料信息放入相应消息，没有接入外部模板管理。无论怎么拼接，简历正文都只作为数据处理，不能让其中的指令改变任务。
>
> 原结构化和改写同样使用 Java 文本块，不能因为 resources/prompts 有 .st 就认为模板已生效。初次改写把 customPrompt 追加到 system；对话重写把历史拼进 user 消息。这些实际消息位置和来源都影响指令边界，当前没有统一的总上下文预算。

**追问：模板文件放到外部，就能实时修改生效吗？**

> 不一定。要看文件何时加载、是否缓存，以及更新后是否重新构造请求。文件放在外部只是维护方式，不会自动获得热更新能力，项目当前也没有实现这套机制。

**原项目继续学习：** [Q135](面试问答.md#q135)、[Q138](面试问答.md#q138)、[Q150](面试问答.md#q150)。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)目前使用 Java 文本块和 user 参数拼接，没有接入 `PromptTemplate` 模板文件或模板热更新系统。

<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q7](#spring-g1)；另见 [G2 Q5](#spring-g2)。

**要点：** Prompt 组织消息与选项；模板通过变量渲染复用指令结构，system/user 等消息承担不同角色。资料中的文本即便像指令，也不能因此成为可信系统规则。外部化模板有利于维护，但是否热更新取决于加载与部署方式。[官方 Prompts](https://docs.spring.io/spring-ai/reference/api/prompt.html)

### S05 call() 与 stream() 有什么区别，流式就更快吗？

> call() 用同步方式获取结果，stream() 则提供逐步返回的响应式流。流式可能让用户更早看到部分内容，但不一定缩短完整生成时间；对外推送还要处理缓冲、取消和结果完整性。项目新分析在后台同步调用模型，前端轮询任务状态，目前没有这条业务的 SSE 推送。

**追问：流式输出是不是一定更快？**

> 不一定。首段内容可能更早出现，但完整结果未必更早结束，而且片段还不能直接作为完整报告保存。我会分别测首次可见时间和整项任务耗时。

**项目对照：** 新证据分析在后台执行同步 `call()`；[报告页](../frontend/src/app/evidence-analyses/[id]/page.tsx)每 2 秒轮询状态。当前没有 Spring AI 流式报告或新业务 SSE。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q3](#spring-g1)；另见 [G2 Q10、Q32](#spring-g2)。

**要点：** `call()`提供同步结果取得方式，`stream()`返回响应式增量流；流式可提前展示部分输出，不能据此保证总生成更快。对外提供 SSE 时还要处理代理缓冲、超时与取消，并区分收到片段和得到完整业务结果。[官方 Chat Client API](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

</details>

### S06 如何将模型输出转成 Java record？entity() 能保证正确吗？

> 可以用 entity 把模型输出转换成 Java record 等类型。默认转换会提供格式说明并解析返回文本，但模型仍可能输出缺字段或错误值。项目转换后还运行 EvidenceValidator，检查要求、ID 和引用，失败时由阶段循环最多再尝试一次。转换成功只说明结构能使用，不代表事实正确。
>
> 原改写用 entity(RewriteGeneration.class) 转换外层结构，但 verificationJson 是模型给出的字符串。非空时直接保存，没有独立事实验证器去核对其中每条结论；默认“待人工确认”也不是自动核验结果。因此新旧流程的校验强度需要分别说明。

**追问：entity()解析失败，是不是框架必然自动重试？**

> 不是必然自动重试。默认转换、可选 Schema 修复和业务重试是不同机制。当前两次阶段尝试来自 Java 循环，不能因为在线文档介绍某个开关，就认为项目已经启用。

**原项目继续学习：** [Q136](面试问答.md#q136)。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)调用 `entity(Evidence.Extraction.class)`等，再交给 [EvidenceValidator](../backend/src/main/java/com/resumeai/compass/EvidenceValidator.java)。本项目最多两次阶段尝试来自 Java 循环，不是“只要调用 entity 就保证自动重试”。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q4](#spring-g1)；另见 [G2 Q6、Q26](#spring-g2)。

**要点：** 默认输出转换在调用前提供格式说明、调用后解析文本；`BeanOutputConverter`帮助映射 Java 类型。这是尽力转换，不能保证模型按要求返回，也不能替代字段、引用和业务校验；解析失败的纠错策略需要明确配置或业务处理。[官方 Output Converters](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)

### S07 JSON Mode、Schema 约束与 Prompt 格式要求有什么区别？

> Prompt 格式要求主要靠模型遵守指令；JSON Mode 关注生成合法 JSON；原生 Schema 约束则把结构要求传给供应商，由其支持的机制约束输出。它们都受模型能力影响。即使结构完全符合，也仍可能引用不存在的内容或作出错误判断，所以业务校验不能省。

**追问：模型返回了合法JSON，可以说已启用Schema约束解码吗？**

> 不能从输出反推机制。要检查请求选项、模型支持和实际调用代码。当前证据流程没有显式开启所述原生输出约束，所以我会按 entity 转换和后端校验介绍实现。

**项目对照：** 当前证据链未显式启用官方文档所述的原生结构化输出开关；不能仅凭返回了 JSON 或 `entity()`解析成功，就声称当前模型采用了受 Schema 约束的解码。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q4 的输出约束问题](#spring-g1)、[G2 Q6](#spring-g2)，将原题中的几种约束拆开复习。

**要点：** Prompt 要求格式依赖模型遵守；JSON Mode 与按指定 JSON Schema 约束不是同一层保证。原生结构化输出将约束交给供应商 API，仍受模型及支持的 Schema 范围限制；结构匹配也不能证明事实正确。[官方 Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html)

<a id="sa08"></a>
### S08 Advisor 是什么，执行顺序为什么重要？

> Advisor 用来在 ChatClient 调用前后加入记忆、检索或统计等处理。getOrder 值小的通常先处理请求、后处理响应。例如 A 为 10、B 为 20，顺序就是 A 请求、B 请求、模型、B 响应、A 响应。同值顺序没有保证，因此它看到什么上下文、统计覆盖哪里，都要结合顺序判断。

**追问：把统计Advisor写在注册列表最前面，就一定最外层吗？**

> 不一定，主要看 getOrder 和实际调用链。项目 Capture 使用 Integer.MIN_VALUE+100，等 nextCall 返回后读取用量。还需要明确它在工具循环中的位置，不能仅按注册列表推断统计范围。

**项目对照：** [AnalysisMetrics.Capture](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)返回 `Integer.MIN_VALUE + 100`，在 `chain.nextCall(request)`返回后记录响应用量；不能只按注册语句的书写顺序推断运行顺序。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G1 Q5](#spring-g1)、[G2 Q24](#spring-g2)。

**要点：** Advisor 在 ChatClient 请求/响应链中加入处理；较小的 `getOrder()`先处理请求、后处理响应，同值顺序不保证。顺序会改变某项逻辑看到的上下文，以及它包围一轮调用还是工具循环的范围。[官方 Advisors API](https://docs.spring.io/spring-ai/reference/api/advisors.html)

</details>

<a id="sa09"></a>
### S09 怎样写自定义 Advisor 来统计调用？

> 同步统计可以实现 CallAdvisor，提供名称、顺序和 adviseCall。进入时准备本次统计，调用 chain.nextCall 继续执行，返回后从响应中读取用量。项目每次阶段尝试创建独立 Capture，只记录数值；异常和耗时还结合阶段的 finally 处理。流式统计则需要另外考虑 StreamAdvisor。

**追问：成功响应里有usage，为什么失败还要单独记？**

> 因为异常时可能根本没有正常响应，返回后的读取逻辑就不会执行。项目在 finally 中补记工具次数、失败和耗时，用量拿不全就标为不完整，避免把失败调用误记成零消耗。

**项目对照：** [AnalysisMetrics.Capture](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)是现成实例，每次尝试新建，仅记录数值；失败路径在模型阶段的 `finally`中补记。返回用量缺失时保留“不完整”标记，不将缺失记成零。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G2 Q25](#spring-g2)，自定义拦截处理。

**要点：** 同步实现 `CallAdvisor`，提供名称、顺序和 `adviseCall`；需要继续链路时调用 `chain.nextCall`，随后读取响应。流式对应 `StreamAdvisor`，不能把同步实现当作已覆盖流式观测。[官方 Advisors API](https://docs.spring.io/spring-ai/reference/api/advisors.html)

</details>

### S10 @Tool 如何注册，模型到底执行了什么？

> 先用 @Tool 描述 Java 方法的用途和参数，再把工具对象通过 tools 等方式显式注册到调用中。模型根据说明返回工具名和参数，Spring AI 在应用里执行方法，再把结果交回模型。项目还在方法内检查 ID 与次数，真正的访问限制不是由注解文字保证的。
>
> 原改写注册的是 ResumeOptimizationTools 的 retrieveGuidance 与 calculateMatchScore 两个方法，参数来自模型，不具备新工具那样的固定快照绑定和四次限制。提示词要求先调用工具，也不能代替执行顺序与次数验证。

**追问：工具说明写成“只允许当前用户访问”，就能保证权限了吗？**

> 不能。工具说明是给模型理解的，授权要由后端强制执行。当前工具校验绑定快照，未来多用户场景还需要根据可信身份检查归属，不能相信模型自己填的用户信息。

**原项目继续学习：** [Q129](面试问答.md#q129)、[Q134](面试问答.md#q134)。

**项目对照：** [ResumeOptimizationTools](../backend/src/main/java/com/resumeai/agent/ResumeOptimizationTools.java)封装知识检索和规则评分；[JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)只读当前快照，内部再检查范围与访问次数。

### S11 Spring AI 2.0 的工具循环由谁驱动？

> 在 Spring AI 2.0 中，工具循环由 ChatClient Advisor 链中的 ToolCallingAdvisor 驱动，负责模型请求、工具执行和后续调用的衔接，具体工具回调交给 ToolCallingManager。业务侧注册工具并实现范围限制即可。直接使用底层 ChatModel 时，不能再按旧版模型层内置循环的假设理解。

**追问：旧教程里的ToolCallAdvisor能直接照抄吗？**

> 不能直接照抄。要先核对项目版本和类名，旧 ToolCallAdvisor 从 2.0.0 起标记弃用并指向 ToolCallingAdvisor。工具名称解析与显式注册也有版本差异，应按锁定版本确认，而不是拿 main 分支示例直接套用。

**项目对照：** 新模型通过 ChatClient 注册工具，业务没有手写通用执行循环。官方 [旧类源码](https://github.com/spring-projects/spring-ai/blob/main/spring-ai-client-chat/src/main/java/org/springframework/ai/chat/client/advisor/ToolCallAdvisor.java)标记 `ToolCallAdvisor`自 2.0.0 弃用，阅读旧教程时须注意它与 `ToolCallingAdvisor`的名称差异。

### S12 ToolContext 与模型生成参数有什么区别？

> 模型生成的参数来自不可信输出，不能拿它当登录身份。ToolContext 则由应用直接提供给工具，不作为模型生成的参数传递。工具仍要检查资源归属和返回字段，因为结果可能回到模型。项目当前通过构造器绑定固定快照，没有使用 ToolContext。

**追问：用户ID放进ToolContext，是不是所有数据都不会发给模型？**

> 不能这样推断。只能说 ToolContext 这部分本身不作为模型参数传递，工具查询后返回什么仍要另外控制。如果把敏感内容放进工具结果，模型依然可能看到。

**项目对照：** 当前 [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)通过构造器绑定运行快照，没有使用 ToolContext。当前 ID 检查也不是未来多用户认证的替代品。

### S13 ChatMemory 怎样保存上下文并隔离会话？

> ChatMemory 决定保留哪些消息，Repository 负责存储，Advisor 把需要的历史加入当前调用。2.x 需要显式提供 conversation ID，还要按用户和会话隔离。窗口记忆只是保留部分对话，不等于完整业务历史。项目旧改写保存的是业务 conversation_history，没有接入 MessageChatMemoryAdvisor。
>
> 原 regenerate 读取 conversation_history，将历史 role/content、原文、上一稿、JD 和用户新要求拼成一条 user 消息；候选快照也存入历史 JSONB。它没有 ChatMemory Advisor，也没有对全部历史实施窗口裁剪；正文的 8000 字符限制不等于整次请求 Token 限制。

**追问：知道conversation ID，就可以读取那段会话吗？**

> 不应该。会话 ID 只负责定位，不代表访问许可。服务端还要检查当前用户是否拥有这个会话，否则知道 ID 就可能造成越权。

**原项目继续学习：** [Q138](面试问答.md#q138)。

**项目对照：** 原改写将历史保存在 [RewriteDraft](../backend/src/main/java/com/resumeai/domain/rewrite/RewriteDraft.java)及其 `conversation_history`字段；没有接入 `MessageChatMemoryAdvisor`。新分析固定快照与追问会话是业务状态，不应统称为框架长期记忆。

### S14 VectorStore 与 EmbeddingModel 如何配合？

> EmbeddingModel 把文本转成向量，VectorStore 提供文档写入、删除和相似检索接口。检索请求再用 TopK、阈值和过滤条件控制数量、相似度与范围。项目使用 pgvector、HNSW 和余弦距离，表结构是 1024 维；改变模型或维度时，都要检查已有向量和索引是否兼容。
>
> 原知识块通过 vectorStore.add 写入，删除语句明确作用于 vector_store。V1/V2 的 document_chunks 是历史表，V3 才建立当前使用的表。模型空间、字段维度和历史索引都要一致；当前 search 还没有租户过滤和有效的配置阈值过滤。

**追问：相似度0.8能不能解释成答案有80%概率正确？**

> 不能。相似度是检索排序信号，不是答案正确概率。当前 search 还使用 similarityThresholdAll，不能只看到配置中有阈值，就说业务已经按这个阈值过滤。

**原项目继续学习：** [Q131](面试问答.md#q131)、[Q148](面试问答.md#q148)、[Q149](面试问答.md#q149)。

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)使用 `vectorStore.add`与`similaritySearch`。项目配置 HNSW/余弦距离，表结构为 1024 维；改维度要连同 [V3迁移](../backend/src/main/resources/db/migration/V3__create_spring_ai_vector_store.sql)及已有向量数据处理，不能只改配置。[官方 PGvector](https://docs.spring.io/spring-ai/reference/api/vectordbs/pgvector.html)

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G2 Q7、Q16](#spring-g2)。

**要点：** EmbeddingModel 生成向量，VectorStore 提供文档写入、删除和相似检索等抽象；集成可在写入及查询时使用对应向量模型。TopK、相似度门槛与过滤条件解决不同问题，向量距离不能当成答案正确概率。[官方 Vector Databases](https://docs.spring.io/spring-ai/reference/api/vectordbs.html)

### S15 元数据过滤如何限定检索范围？

**追问：有过滤表达式，为什么还不能说已实现多租户知识库？**

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)为块记录文档 ID、标题、类型及块序号，删除按文档 ID metadata 定位；当前搜索没有租户过滤，不应表述成已实现多租户知识库。

### S16 Spring AI ETL 有哪几层，分块是否等于 TokenTextSplitter？

> ETL 可以按职责分成读取、转换和写入。Reader 生成 Document，Transformer 做分块或信息补充，Writer 把结果写到目标存储。具体实现可以不同，项目使用 Tika 提取文本，再按段落和字符长度切分，没有使用 TokenTextSplitter。
>
> 对应原模块，Tika 先提取文本并整理空白，KnowledgeDocument 另行保存知识正文；RagKnowledgeService 再按段落组块，只有超长段落使用 180 字符重叠。文件解析、知识创建和显式建索引是不同入口，不能看见分块就认定使用了框架内置 ETL 全链路。

**追问：代码里有分块逻辑，就算使用了TokenTextSplitter吗？**

> 不算。分块是要做的事情，TokenTextSplitter 是一种具体实现。当前 1800 和 180 的规则使用 Java 字符长度，而且普通段落与超长段落处理不同，不能改称 Token 切分。

**原项目继续学习：** [Q124](面试问答.md#q124)、[Q131](面试问答.md#q131)、[Q132](面试问答.md#q132)。

**项目对照：** 项目使用 [TikaDocumentTextExtractor](../backend/src/main/java/com/resumeai/infrastructure/document/TikaDocumentTextExtractor.java)解析文件，[RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)按段落和字符长度切分。不能把当前的 1800/180 字符规则说成框架 TokenTextSplitter 的 token 策略。

<details>
<summary>题源、原文摘录与补充要点</summary>

**题源：** [G2 Q20](#spring-g2)，文档入库流程。

**要点：** Reader 读取 Document，Transformer 转换文档列表，Writer 写入；典型链路可组合读取器、TokenTextSplitter 和 VectorStore。ETL 是抽象分工，不要求所有应用使用同一种解析器或切分算法。[官方 ETL Pipeline](https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html)

</details>

### S18 Spring AI 有哪些观测能力，Token 怎样记录？

> Spring AI 可以通过 Micrometer 观测模型、客户端、工具和向量存储等操作，响应元数据也可能返回 Token 用量，具体取决于接入和模型。项目目前保存运行级数值统计，没有完整链路平台。没有返回用量就标为未知，提示词、输出和工具正文也不随意导出。
>
> 现有 AnalysisMetrics 记录的是新增证据分析的尝试，不会自动统计原结构化和改写调用。原网关、改写方法有日志和回退，但不能因此声称它们也有同样完整的运行级 Token 汇总。后续接入要分别考虑工具循环、失败缺失和来源标记。

**追问：返回的Token统计，能直接当成最终账单吗？**

> 不能直接等同。费用还受供应商和缓存计费口径影响，网络中断也可能导致已经消耗但没有收到用量。项目保留已知部分，不完整总量标成 null 和 usageComplete=false，需要时再与供应商记录核对。

### S20 如何处理模型重试、超时和成本叠加？

> 我会把客户端重试、工具往返和阶段重试分别计算，因为一次阶段尝试也可能包含多次模型请求。当前请求超时选项是 60 秒，maxRetries 为 0；每阶段最多尝试两次，每次工具访问最多四次。它们限制了局部行为，但整项任务的总时限还没有实现。
>
> 这组显式请求选项与次数限制来自新增 SpringAiEvidenceModel。原结构化和改写走各自 ChatClient 调用与异常回退，没有在这些方法中设置相同的阶段循环和四次工具上限；默认请求行为还要看实际客户端配置，不能把新模块参数当成全局保证。

**追问：有60秒超时和两次尝试，为什么还可能等更久？**

> 因为任务可能先排队，再执行提取、核对及各自重试，工具结果返回后也可能继续请求模型。单次请求选项不能代表整项任务时长，因此还可能等得更久，后续需要增加端到端截止时间。

**原项目继续学习：** [Q126](面试问答.md#q126)、[Q129](面试问答.md#q129)、[Q137](面试问答.md#q137)、[Q151](面试问答.md#q151)。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)显式设单次调用选项 `timeout(60秒)`、`maxRetries(0)`，每阶段业务最多尝试两次，每次工具读取上限四次。这些设置不能换算成整项任务 60 秒完成或只发两次模型请求；也不能将开发者选项当作生产压测结论。

### U07 JPA 的受管理、游离、脏检查、flush 和 commit 怎样区分？
