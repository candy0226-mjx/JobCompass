## 一、Spring AI 相关概念与 Agent 工程

### 01 Java AI 框架如何选型

原文：[LangChain4j 主要解决了哪些问题？](https://xiaolinnote.com/ai/langchain/langchain4j.html)，重点读“什么时候适合 LangChain4j？”与“面试总结”。

> 原文短摘录：强依赖 Spring 编程模型时要对比 Spring AI

**来源要点（转述）：** Java AI 框架将模型、工具、记忆、检索与输出转换组织为应用接口，选型应结合已有技术体系。接口统一后仍需验证各厂商能力差异；复杂流程的恢复和事务不能仅靠模型循环。

**项目对照：** [依赖声明](../backend/pom.xml)使用 Spring AI 2.0.0 与 Spring Boot 4.1.0；[SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)使用 `ChatClient`。项目没有接入 LangChain4j、LangGraph 或 Spring AI Alibaba，不能把文章里的接口名当成本项目实现。

### 02 Workflow、Agent、Tools 的区别

原文：[Workflow，Agent，Tools 的概念和区别](https://xiaolinnote.com/ai/agent/3_workflow_tools.html)，重点读末尾三者对比与总结。

> 原文短摘录：关键不是节点类型，而是控制流由谁掌握

**来源要点（转述）：** 工具提供具体执行能力；Agent 在运行中由模型选择下一步；Workflow 由程序安排主要步骤。可以把模型判断嵌入预设流程，不必把所有环节交给模型自主规划。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)由 Java 安排“提取要求→核对经历”，每阶段注册只读工具；[BudgetPlanner](../backend/src/main/java/com/resumeai/compass/BudgetPlanner.java)由 Java 规则合并和安排任务。当前不是多 Agent 自主协作系统。

### 03 上下文工程与 Prompt、Memory 的区别

原文：[Agent 的上下文工程怎么设计？](https://xiaolinnote.com/ai/agent/17_context_engineering.html)，重点读概念区别、Token 预算和逐步装配。

> 原文短摘录：这一轮让模型看到什么

**来源要点（转述）：** 除了指令写法，还应选择当前任务需要的状态、资料、工具定义和结果，控制体积并区分可信指令与外部文本。压缩效果应同时看事实保留、任务质量和成本，不能只比较 Token。

**项目对照：** [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)的 FULL/COMPACT 返回不同快照结构；COMPACT 移除重复元数据，保留 ID 和全部原文分段，没有实现摘要式长期记忆。历史对照见[评估结果](jobcompass-evaluation-comparison.json)，小样本不代表普遍收益。

### 04 Agent 效果如何评估

原文：[如何评估一个 Agent 的效果？](https://xiaolinnote.com/ai/agent/19_evaluation.html)，重点读分层评测、评测集、发布门禁。

> 原文短摘录：Agent 评测不能只看最终答案

**来源要点（转述）：** 既看任务结果，也看工具与参数、执行过程和约束；结合延迟、Token、稳定性分析。评测样例需有明确成功条件，确定性校验优先，开放质量可加人工评价；版本比较应分析失败类型与重复运行表现。

**项目对照：** [AnalysisMetrics](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)记录阶段尝试、耗时、工具次数、失败码及返回用量；[既有评估文件](jobcompass-evaluation-comparison.json)保留 40 组 FULL/COMPACT 对照。现有记录不等于完整 Trace 平台或线上 A/B 系统，标签一致率也不是通用准确率。

### 05 Function Calling 与 MCP 的区别

原文：[MCP 和 Function Calling 有什么区别？](https://xiaolinnote.com/ai/tools/6_mcp_vs_fc.html)，重点读两者分层和选型。

> 原文短摘录：两者是不同抽象层次的东西

**来源要点（转述）：** Function Calling 涉及模型表达调用意图及参数，宿主程序执行工具并回传结果；MCP 侧重工具接入、发现与复用的协议。两者可以配合，不能仅因为函数能被模型调用，就称其为 MCP 服务。

**项目对照：** [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)使用 `@Tool`，由 `.tools(tools)` 注册到 ChatClient；当前是应用内工具，没有实现 MCP Server/Client。

### 06 工具格式错误、超时与失败如何处理

原文：[工具调用格式非法、参数错误、超时或失败时如何容错？](https://xiaolinnote.com/ai/tools/18_tool_reliability.html)，重点读错误分类、有界重试、幂等和未知结果。

> 原文短摘录：先分类，再处理

**来源要点（转述）：** 格式不合法、业务参数错误、无权限、瞬时故障及执行结果未知，处理方式不同。有副作用的调用需稳定幂等标识；超时后不能直接认定没执行，必要时先查询结果。重试应限制次数与时间。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)每阶段最多两次尝试，附带纠错信息；工具每次尝试重新创建且最多四次访问。这是模型阶段重试，不等于每个 HTTP 请求最多两次。写入幂等由 [PlanningService.confirm](../backend/src/main/java/com/resumeai/compass/PlanningService.java)负责，当前没有实现文章中的完整熔断、Checkpoint 调度和外部副作用恢复。

### 07 模型查数据库时如何限制权限与泄漏

原文：[如何防止越权、敏感数据泄漏和查询幻觉？](https://xiaolinnote.com/ai/agent/24_database_security.html)，重点读细粒度工具、外部文本注入和结果最小化。

> 原文短摘录：不能把 Prompt 当成安全边界

**来源要点（转述）：** 身份与授权来自可信系统；工具和数据库限制可访问范围，尽量只返回必要字段。工具结果中的文字仍是外部数据。查询合法与业务口径正确需要分别校验，模型自称有权限不能作为授权依据。

**项目对照：** [JobCompassReadTools.check](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)校验当前运行绑定的 ID，只暴露固定快照，没有任意 SQL 和写工具。当前仍是单用户范围，ID 范围检查不代表已经实现多用户认证、租户隔离或完整安全体系。

### 08 人工确认如何落实到程序

原文：[Agent 应该在什么情况下请求人工确认？](https://xiaolinnote.com/ai/agent/28_human_confirmation.html)，重点读确认范围、内容版本、恢复后的条件核验。

> 原文短摘录：批准完成不代表动作一定成功

**来源要点（转述）：** 确认要对应可查看的动作、对象与内容，保存有效范围和版本；执行时仍需核验条件与实际结果。相同决定重复到达要避免重复执行，明确授权范围内的查询与准备无需反复打断用户。

**项目对照：** [PlanningService.confirm](../backend/src/main/java/com/resumeai/compass/PlanningService.java)结合行锁、确认键和内容哈希；[ExperienceService.confirm](../backend/src/main/java/com/resumeai/compass/experience/ExperienceService.java)保存用户确认的证据卡快照。二者是业务确认流程，不是跨系统通用审批引擎，也不会自动向外投递简历。

## 二、RAG 与知识库

### 09 RAG 的完整流程

原文：[什么是 RAG？完整流程是什么？](https://xiaolinnote.com/ai/rag/1_whatisrag.html)，重点读离线索引与在线检索生成。

> 原文短摘录：离线负责建库，在线负责检索和生成

**来源要点（转述）：** 文档先解析、切分、向量化并建立索引；查询时检索相关片段，再将资料与问题交给模型。文章还介绍查询改写和重排，它们是可按场景选择的环节，不能据此宣称所有 RAG 都必须具备同一条链。

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)有 `index/search/deleteIndex`；原工具 [ResumeOptimizationTools](../backend/src/main/java/com/resumeai/agent/ResumeOptimizationTools.java)可使用知识检索。新证据链读取固定简历/JD 快照，不能把该链称作向量召回分析。

### 10 文档分块与粒度如何选择

原文：[文档存储与 Chunking 策略](https://xiaolinnote.com/ai/rag/4_chunking.html)，重点读固定窗口、语义边界、父子块的取舍。

> 原文短摘录：粒度选择没有银弹

**来源要点（转述）：** 块太大影响局部匹配和输入预算，块太小容易失去上下文；重叠、结构边界和父子块分别解决不同问题。文档类型与实际召回评估决定取舍，文章中的 token 范围是示例起点。

**项目对照：** [RagKnowledgeService.splitIntoChunks](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)先聚合段落，长段落按最多 1800 个 Java 字符单位拆分并重叠 180；普通段落块没有统一加重叠。这不是 1800 token，也没有实现语义切分、父子检索或 Late Chunking。

### 11 Embedding 是什么，怎样选模型

原文：[Embedding 的含义、选择与评估](https://xiaolinnote.com/ai/rag/6_embedding.html)，重点读业务数据评测。

> 原文短摘录：语义相近的文本向量距离近

**来源要点（转述）：** Embedding 把文本映射到可比较的数值空间。候选模型要结合语言、领域、部署约束和成本，用业务问题与正确片段评估 Hit@K；排行榜和别人项目里的示例数字不能替代自己的测试。

**项目对照：** 本项目聊天与向量化可分别配置，向量索引依赖向量模型；[依赖](../backend/pom.xml)包含 pgvector 集成。改模型时还要检查维度和已有索引，不能只改模型名称。文章中的 Hit@K 示例不代表本项目实测结果。

### 12 向量检索与关键词检索如何互补

原文：[向量检索和关键词检索的区别](https://xiaolinnote.com/ai/rag/11_retrieval_types.html)，重点读精确词、语义与混合检索。

> 原文短摘录：两者是互补关系

**来源要点（转述）：** 词项检索擅长处理明确名称与术语，向量检索适合语义近似表达；混合方案可多路召回后融合排名。应区分多路融合与失败后备用查询，两者的执行方式和效果不同。

**项目对照：** [RagKnowledgeService.search](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)先调用向量检索，异常或无结果才走文本查询，TopK 被限制在 1–10。现有文本兜底不能说成 BM25、并行混合召回、RRF 或 Rerank；这些均未在当前实现中接入。

### 13 怎样降低幻觉并核对引用

原文：[如何规避 RAG 系统中大模型的幻觉？](https://xiaolinnote.com/ai/rag/17_hallucination.html)，重点读引用核查、检索门控和结构化溯源。

> 原文短摘录：强制 LLM 输出时带上来源编号

**来源要点（转述）：** 取回了资料仍可能出现额外推断；可结合资料约束、证据不足时拒答、来源标识和生成后核查降低风险。格式正确、来源存在和结论被证据支持，是不同层次的要求。

**项目对照：** [EvidenceValidator](../backend/src/main/java/com/resumeai/compass/EvidenceValidator.java)检查要求 ID、段落 ID、逐字引用和判断字段；新流程虽不是 RAG，也采用可追溯证据约束。`entity(...)` 成功不代表事实正确，逐字引用正确也不保证语义判断正确，仍保留人工复核。

### 14 何时用 RAG，何时直接读取资料

原文：[RAG 与 Agent 自主文件检索应该如何选型？](https://xiaolinnote.com/ai/rag/23_rag_vs_file_search.html)，重点读资料规模、更新方式、探索需求和证据完整性。

> 原文短摘录：重点是用合适的代价获得足够且可核对的证据

**来源要点（转述）：** 大量重复局部查询可复用索引；需沿新线索探索时可用自主检索；少量材料需要整体理解时可直接读全文。两种检索也可组合，命中若干候选并不能证明已覆盖全部资料。

**项目对照：** 原知识库用向量索引提供写作知识；新分析通过 [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)读取固定版本原文。它是受限快照读取，不是模型自由搜索本机文件；引用范围与资料版本有明确边界。

## 三、与当前后端直接相关的基础八股

本节每个专题只摘取少量内容。原页面篇幅较大，完整问答与图解以原文为准。

### 15 IoC、依赖注入与 Spring Boot 装配

原文：[Spring 面试题](https://xiaolincoding.com/interview/spring.html)，站内查找 `IOC`、`依赖注入`、`自动装配`。

> 原文短摘录：对象的创建和对象间的依赖关系管理

**来源要点（转述）：** 容器组织 Bean 及依赖；Boot 按依赖、条件和配置提供默认装配。学习时分清容器管理与业务对象自行创建。

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)通过构造器注入 Builder、校验器等；每次尝试的工具由代码 `new` 出来。Boot 自动配置的具体加载机制需按当前版本核对，不能直接套用旧版 `spring.factories` 教程。

### 16 Spring 事务与代理边界

原文：[Spring 面试题](https://xiaolincoding.com/interview/spring.html)，站内查找 `事务`、`代理`。

> 原文短摘录：绕过代理

**来源要点（转述）：** 声明式事务受代理、方法可代理性和回滚规则影响；理解事务是否真正覆盖所需操作比只背注解更关键。

**项目对照：** 新业务 [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)、[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)使用 `TransactionTemplate` 控制短事务，模型调用在其外部。原 [ResumeRewriteService](../backend/src/main/java/com/resumeai/application/rewrite/ResumeRewriteService.java)仍有既有事务结构，不能把新模块的取舍描述成全项目都已完成的改造。

### 17 线程池参数、任务队列与执行顺序

原文：[Java 并发编程面试题](https://xiaolincoding.com/interview/juc.html)，站内查找 `线程池的参数有哪些`、`工作原理`。

> 原文短摘录：复用线程、控制并发数量

**来源要点（转述）：** 结合核心/最大线程、存活时间、队列、工厂及拒绝处理理解任务接纳过程；队列有无上限会影响扩容与积压。

**项目对照：** [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)采用 2 个工作线程、8 个等待名额、`AbortPolicy`；[ExperienceService](../backend/src/main/java/com/resumeai/compass/experience/ExperienceService.java)采用独立 1 线程和 4 个等待名额。配置是资源边界，不是经过压测的吞吐承诺。

### 18 拒绝策略与原子计数

原文：[Java 并发编程面试题](https://xiaolincoding.com/interview/juc.html)，站内查找 `拒接策略`、`AtomicInteger`。

> 原文短摘录：提交任务的线程

**来源要点（转述）：** CallerRunsPolicy 占用提交方；AbortPolicy 使接纳失败可见。原子类保护单次更新，不会自动提供整个业务事务。

**项目对照：** 队列拒绝后 [EvidenceService](../backend/src/main/java/com/resumeai/compass/EvidenceService.java)保存失败状态并返回 429；工具用 `AtomicInteger.incrementAndGet()`计数并限制访问。进程重启将遗留任务标为 `INTERRUPTED`，没有持久队列自动接管。

### 19 HashMap、HashSet 与业务去重

原文：[Java 集合面试题](https://xiaolincoding.com/interview/collections.html)，站内查找 `HashMap`、`HashSet`、`equals`。

> 原文短摘录：数组 + 链表 / 红黑树

**来源要点（转述）：** 需要理解哈希定位、碰撞、扩容及相等性；集合选型还取决于顺序与并发要求。普通 Map 不能因放在 Spring 服务中就自动变成线程安全。

**项目对照：** [BudgetPlanner](../backend/src/main/java/com/resumeai/compass/BudgetPlanner.java)使用集合组织技能与任务合并；[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)用 Set 检查重复报告/岗位。进程内去重不代替数据库唯一约束，预算排序也不是全局最优求解。

### 20 ACID、锁、版本与幂等

原文：[MySQL 面试题](https://xiaolincoding.com/interview/mysql.html)，站内查找 `ACID`、`事务`、`锁`。这里只选通用概念。

> 原文短摘录：原子性、一致性、隔离性和持久性

**来源要点（转述）：** 事务保证一组相关变更的提交边界；并发更新还需理解隔离、锁与约束。数据库的具体行为依赖实现与配置。

**项目对照：** [SnapshotService](../backend/src/main/java/com/resumeai/compass/SnapshotService.java)锁父记录分配版本号；[PlanningService](../backend/src/main/java/com/resumeai/compass/PlanningService.java)组合 `FOR UPDATE`、版本条件、确认键、内容哈希及唯一约束。当前使用 PostgreSQL 17，不可套用 InnoDB 的聚簇索引、间隙锁或默认隔离级别；隔离细节见 [PostgreSQL 17 官方文档](https://www.postgresql.org/docs/17/transaction-iso.html)。

### 21 Redis 缓存雪崩、击穿与穿透

原文：[Redis 面试题](https://xiaolincoding.com/interview/redis.html)，站内查找 `缓存雪崩、击穿、穿透` 与 `数据缓存一致性`。

> 原文短摘录：事务提交成功后，再删除缓存

**来源要点（转述）：** 区分大量缓存同时失效、热点单键失效与查询不存在数据；缓存与数据库之间存在失败窗口，需要根据可接受的旧数据时间选择失效、重试等措施，不能天然承诺强一致。

**项目对照：** Redis 是上游保留基础服务；[RedisHealthService](../backend/src/main/java/com/resumeai/infrastructure/redis/RedisHealthService.java)提供健康检查。新分析状态存在 PostgreSQL，队列在 JVM 内存中，没有把上述缓存治理、Redis 队列、分布式锁或 Bloom Filter 做成当前成果。本条按基础扩展复习。

### S02 ChatClient 与 ChatModel 如何分工？

**题源：** [G1 Q2](#spring-g1)；另见 [G2 Q3](#spring-g2)。

**要点：** ChatModel 是模型调用抽象；ChatClient 在其上提供链式消息构建、默认值、Advisor、工具及类型化结果等便利能力。ChatClient 同时支持同步与流式，“fluent API”不意味着每次调用都是流式。[官方 Chat Client API](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

### S04 PromptTemplate 与 system/user 消息有什么用？

**题源：** [G1 Q7](#spring-g1)；另见 [G2 Q5](#spring-g2)。

**要点：** Prompt 组织消息与选项；模板通过变量渲染复用指令结构，system/user 等消息承担不同角色。资料中的文本即便像指令，也不能因此成为可信系统规则。外部化模板有利于维护，但是否热更新取决于加载与部署方式。[官方 Prompts](https://docs.spring.io/spring-ai/reference/api/prompt.html)

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)目前使用 Java 文本块和 user 参数拼接，没有接入 `PromptTemplate` 模板文件或模板热更新系统。

### S05 call() 与 stream() 有什么区别，流式就更快吗？

**题源：** [G1 Q3](#spring-g1)；另见 [G2 Q10、Q32](#spring-g2)。

**要点：** `call()`提供同步结果取得方式，`stream()`返回响应式增量流；流式可提前展示部分输出，不能据此保证总生成更快。对外提供 SSE 时还要处理代理缓冲、超时与取消，并区分收到片段和得到完整业务结果。[官方 Chat Client API](https://docs.spring.io/spring-ai/reference/api/chatclient.html)

**项目对照：** 新证据分析在后台执行同步 `call()`；[报告页](../frontend/src/app/evidence-analyses/[id]/page.tsx)每 2 秒轮询状态。当前没有 Spring AI 流式报告或新业务 SSE。

<a id="sa06"></a>
### S06 如何将模型输出转成 Java record？entity() 能保证正确吗？

**题源：** [G1 Q4](#spring-g1)；另见 [G2 Q6、Q26](#spring-g2)。

**要点：** 默认输出转换在调用前提供格式说明、调用后解析文本；`BeanOutputConverter`帮助映射 Java 类型。这是尽力转换，不能保证模型按要求返回，也不能替代字段、引用和业务校验；解析失败的纠错策略需要明确配置或业务处理。[官方 Output Converters](https://docs.spring.io/spring-ai/reference/api/structured-output/converters.html)

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)调用 `entity(Evidence.Extraction.class)`等，再交给 [EvidenceValidator](../backend/src/main/java/com/resumeai/compass/EvidenceValidator.java)。本项目最多两次阶段尝试来自 Java 循环，不是“只要调用 entity 就保证自动重试”。

<a id="sa07"></a>
### S07 JSON Mode、Schema 约束与 Prompt 格式要求有什么区别？

**题源：** [G1 Q4 的输出约束问题](#spring-g1)、[G2 Q6](#spring-g2)，将原题中的几种约束拆开复习。

**要点：** Prompt 要求格式依赖模型遵守；JSON Mode 与按指定 JSON Schema 约束不是同一层保证。原生结构化输出将约束交给供应商 API，仍受模型及支持的 Schema 范围限制；结构匹配也不能证明事实正确。[官方 Provider-Native Structured Output](https://docs.spring.io/spring-ai/reference/api/structured-output/native.html)

**项目对照：** 当前证据链未显式启用官方文档所述的原生结构化输出开关；不能仅凭返回了 JSON 或 `entity()`解析成功，就声称当前模型采用了受 Schema 约束的解码。

<a id="sa08"></a>
### S08 Advisor 是什么，执行顺序为什么重要？

**题源：** [G1 Q5](#spring-g1)、[G2 Q24](#spring-g2)。

**要点：** Advisor 在 ChatClient 请求/响应链中加入处理；较小的 `getOrder()`先处理请求、后处理响应，同值顺序不保证。顺序会改变某项逻辑看到的上下文，以及它包围一轮调用还是工具循环的范围。[官方 Advisors API](https://docs.spring.io/spring-ai/reference/api/advisors.html)

**项目对照：** [AnalysisMetrics.Capture](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)返回 `Integer.MIN_VALUE + 100`，在 `chain.nextCall(request)`返回后记录响应用量；不能只按注册语句的书写顺序推断运行顺序。

<a id="sa09"></a>
### S09 怎样写自定义 Advisor 来统计调用？

**题源：** [G2 Q25](#spring-g2)，自定义拦截处理。

**要点：** 同步实现 `CallAdvisor`，提供名称、顺序和 `adviseCall`；需要继续链路时调用 `chain.nextCall`，随后读取响应。流式对应 `StreamAdvisor`，不能把同步实现当作已覆盖流式观测。[官方 Advisors API](https://docs.spring.io/spring-ai/reference/api/advisors.html)

**项目对照：** [AnalysisMetrics.Capture](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)是现成实例，每次尝试新建，仅记录数值；失败路径在模型阶段的 `finally`中补记。返回用量缺失时保留“不完整”标记，不将缺失记成零。

<a id="sa10"></a>
### S10 @Tool 如何注册，模型到底执行了什么？

**题源：** [G2 Q12](#spring-g2)；GitHub 延伸读 [Spring AI工具调用实战](https://github.com/shining-stars-l/javaup/blob/master/docs/56-AI%E5%A4%A7%E6%A8%A1%E5%9E%8B%E9%9D%A2%E8%AF%95%E8%AF%A6%E8%A7%A3/20-FunctionCall%E8%AF%A6%E7%BB%86%E8%A7%A3%E6%9E%90/02-SpringAI%E5%B7%A5%E5%85%B7%E8%B0%83%E7%94%A8%E5%AE%9E%E6%88%98.md)。

**要点：** 工具定义包括名称、说明和入参 Schema；`@Tool`与`@ToolParam`帮助生成定义，再通过 `.tools(...)`显式提供。模型返回调用意图和参数，实际 Java 方法由应用执行；注解描述不承担权限校验。[官方 Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html)

**项目对照：** [ResumeOptimizationTools](../backend/src/main/java/com/resumeai/agent/ResumeOptimizationTools.java)封装知识检索和规则评分；[JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)只读当前快照，内部再检查范围与访问次数。

<a id="sa11"></a>
### S11 Spring AI 2.0 的工具循环由谁驱动？

**题源：** [G2 Q3、Q14](#spring-g2)，模型层调用与接管工具执行。

**要点：** 2.0 将循环放到 ChatClient 的 Advisor 链，由 `ToolCallingAdvisor`驱动并通过 `ToolCallingManager`执行回调，再把结果交回模型。直接调用底层 ChatModel 不能沿用 1.x 内置执行循环的假设。[官方 2.0 工具架构说明](https://spring.io/blog/2026/06/15/spring-ai-composable-tool-calling/)

**项目对照：** 新模型通过 ChatClient 注册工具，业务没有手写通用执行循环。官方 [旧类源码](https://github.com/spring-projects/spring-ai/blob/main/spring-ai-client-chat/src/main/java/org/springframework/ai/chat/client/advisor/ToolCallAdvisor.java)标记 `ToolCallAdvisor`自 2.0.0 弃用，阅读旧教程时须注意它与 `ToolCallingAdvisor`的名称差异。

<a id="sa12"></a>
### S12 ToolContext 与模型生成参数有什么区别？

**题源：** [G2 Q13](#spring-g2)，工具调用中的身份来源。

**要点：** ToolContext 可由应用向工具传递用户、租户等运行信息，这部分上下文本身不作为模型参数发送；工具返回结果仍可能回传模型。身份应来自可信登录态，工具仍需校验资源归属，不能信任模型自报身份。[官方 Tool Context](https://docs.spring.io/spring-ai/reference/api/tools.html#_tool_context)

**项目对照：** 当前 [JobCompassReadTools](../backend/src/main/java/com/resumeai/compass/JobCompassReadTools.java)通过构造器绑定运行快照，没有使用 ToolContext。当前 ID 检查也不是未来多用户认证的替代品。

<a id="sa13"></a>
### S13 ChatMemory 怎样保存上下文并隔离会话？

**题源：** [G1 Q6](#spring-g1)；另见 [G2 Q9、Q23](#spring-g2)。

**要点：** ChatMemory 管理保留哪些消息，Repository 负责存储，Advisor 将相关历史带入调用。2.x 要显式提供 conversation ID；ID 应按用户和会话设计，但 ID 本身不是授权凭证。窗口记忆也不等于完整业务审计历史。[官方 Chat Memory](https://docs.spring.io/spring-ai/reference/api/chat-memory.html)

**项目对照：** 原改写将历史保存在 [RewriteDraft](../backend/src/main/java/com/resumeai/domain/rewrite/RewriteDraft.java)及其 `conversation_history`字段；没有接入 `MessageChatMemoryAdvisor`。新分析固定快照与追问会话是业务状态，不应统称为框架长期记忆。

<a id="sa14"></a>
### S14 VectorStore 与 EmbeddingModel 如何配合？

**题源：** [G2 Q7、Q16](#spring-g2)。

**要点：** EmbeddingModel 生成向量，VectorStore 提供文档写入、删除和相似检索等抽象；集成可在写入及查询时使用对应向量模型。TopK、相似度门槛与过滤条件解决不同问题，向量距离不能当成答案正确概率。[官方 Vector Databases](https://docs.spring.io/spring-ai/reference/api/vectordbs.html)

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)使用 `vectorStore.add`与`similaritySearch`。项目配置 HNSW/余弦距离，表结构为 1024 维；改维度要连同 [V3迁移](../backend/src/main/resources/db/migration/V3__create_spring_ai_vector_store.sql)及已有向量数据处理，不能只改配置。[官方 PGvector](https://docs.spring.io/spring-ai/reference/api/vectordbs/pgvector.html)

<a id="sa15"></a>
### S15 元数据过滤如何限定检索范围？

**题源：** [G2 Q17](#spring-g2)。

**要点：** Document 可带来源、分组等 metadata，SearchRequest 的过滤表达式在检索时限定范围。身份相关条件应由可信业务上下文构造，搜索和删除都要考虑同一范围；有过滤接口不代表自动完成用户授权。[官方 Vector Databases](https://docs.spring.io/spring-ai/reference/api/vectordbs.html)

**项目对照：** [RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)为块记录文档 ID、标题、类型及块序号，删除按文档 ID metadata 定位；当前搜索没有租户过滤，不应表述成已实现多租户知识库。

<a id="sa16"></a>
### S16 Spring AI ETL 有哪几层，分块是否等于 TokenTextSplitter？

**题源：** [G2 Q20](#spring-g2)，文档入库流程。

**要点：** Reader 读取 Document，Transformer 转换文档列表，Writer 写入；典型链路可组合读取器、TokenTextSplitter 和 VectorStore。ETL 是抽象分工，不要求所有应用使用同一种解析器或切分算法。[官方 ETL Pipeline](https://docs.spring.io/spring-ai/reference/api/etl-pipeline.html)

**项目对照：** 项目使用 [TikaDocumentTextExtractor](../backend/src/main/java/com/resumeai/infrastructure/document/TikaDocumentTextExtractor.java)解析文件，[RagKnowledgeService](../backend/src/main/java/com/resumeai/application/knowledge/RagKnowledgeService.java)按段落和字符长度切分。不能把当前的 1800/180 字符规则说成框架 TokenTextSplitter 的 token 策略。

### S17 两类 RAG Advisor 怎样选择？

**题源：** [G1 Q5](#spring-g1)、[G2 Q18](#spring-g2)，Advisor 与检索增强。

**要点：** QuestionAnswerAdvisor 适合从向量库检索并增强提问的简单链路；RetrievalAugmentationAdvisor 提供更模块化的查询变换、召回和上下文增强。是否需要改写、空结果处理等，应按任务选择并评估。[官方 RAG](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)

**项目对照：** 当前原知识库走工具→RagKnowledgeService，未注册上述 RAG Advisor。新证据分析直接读取绑定版本原文；依赖里存在 advisor 模块不能证明业务已使用它。

### S18 Spring AI 有哪些观测能力，Token 怎样记录？

**题源：** [G2 Q34、Q35](#spring-g2)，成本与观测。

**要点：** 框架通过 Micrometer 观测模型、客户端、工具及向量存储等操作，响应元数据也可提供用量。Prompt、输出和工具内容可能敏感，默认不导出这些正文；指标可用性取决于模型返回及实际接入。[官方 Observability](https://docs.spring.io/spring-ai/reference/observability/index.html)

**项目对照：** [AnalysisMetrics](../backend/src/main/java/com/resumeai/compass/AnalysisMetrics.java)已有数值统计并保存到分析记录，没有完整链路平台。它不保存提示词或工具正文；返回 Token 不是账单，网络中断时也可能无法获知服务端已消耗的用量。

### S19 怎样评价回答质量，而不只验证接口成功？

**题源：** [G2 Q37](#spring-g2)，Java 应用质量评估。

<a id="sa20"></a>
### S20 如何处理模型重试、超时和成本叠加？

**题源：** [G2 Q33、Q34](#spring-g2)，稳定性与预算。

**要点：** 需要分清模型客户端的请求重试、工具循环及业务阶段重试；超时和尝试次数应一起约束。供应商集成提供重试配置，但实际默认值与可重试错误需按版本核对；有副作用的工具还要单独处理幂等和未知结果。[官方 OpenAI Chat 配置](https://docs.spring.io/spring-ai/reference/api/chat/openai-chat.html)

**项目对照：** [SpringAiEvidenceModel](../backend/src/main/java/com/resumeai/compass/SpringAiEvidenceModel.java)显式设单次调用选项 `timeout(60秒)`、`maxRetries(0)`，每阶段业务最多尝试两次，每次工具读取上限四次。这些设置不能换算成整项任务 60 秒完成或只发两次模型请求；也不能将开发者选项当作生产压测结论。

### 常见误区与版本差异

| 常见误区 | 正确理解 |
|---|---|
| 更换供应商只需改配置 | 统一抽象减少适配成本，供应商能力、参数和实际效果仍需验证 |
| entity()解析失败必然自动重试 | 输出转换、显式Schema校验/纠错与业务阶段重试是不同机制 |
| Function Bean通过toolNames()注册的旧写法可直接用于2.0 | 2.0已移除旧的名称解析模式，需显式注册工具对象或ToolCallback |
| 旧式Memory/Advisor构造器适用于所有版本 | 构造方式和接口会演进，按对应版本的Builder与API文档使用 |
| 模板文件外置就能自动热更新 | 文件外置有利于维护，热更新取决于加载与部署机制；当前项目未实现 |
